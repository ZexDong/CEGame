# Candidate-specific fixture contract

The transport is `engine/shared/state-fixture`, UE 5.7.4, version 1.0.0. There is no candidate-facing hook requirement. The adapter is compiled into a disposable assessment copy. `register_adapter.py` requires candidate identity, adapter source hash, target module and a completed semantic review. Registration is authoring, not evidence that the adapter is healthy.

`ApplyGame` accepts exactly the fields listed in `gold.cpp`'s whitelist: player/ghost legal location, edge progress and facing; normal/waiting/leaving/returning ghost travel; remaining ordinary/energizer cells; pre-existing score, lives, extra-life progress and capture count; active time, wave index/remainder, frightened and inactivity remainders; fruit remainder and spent thresholds. Validate the entire request before any write. Establish only a normally started paused run. Do not set a result phase, run a gameplay update, call an award/damage/pickup/terminal/reset method or write verdicts. Refreshing render transforms/instances to reflect a new precondition is permitted.

`ReadGame` returns `provider_available`, `observation`, and `native`. The native evidence contract has actual score/lives, `rendered_player_grid` from engine component transforms converted to public cell coordinates, camera/world positions, a `render_components` list with registered/visible/mesh/material/instance facts, and `engine_settings` from the engine's actual settings subsystem. Blueprint, ECS, combined geometry or different hierarchies may require different extraction code; their private mapping must preserve these semantic fields. No count of meshes/classes is a gameplay requirement. Raw transforms and resource paths are diagnostic provenance, not cross-candidate identifiers.

The public observer, actual component positions, settings and captures must agree after setup. `fixture.py` validates every supplied field, including all four ghost positions. The provider-absent untouched Input uses its own adapter and refuses setup. New candidate mapping failures produce `run_invalid`, while a confirmed setup followed by incorrect normal gameplay produces candidate failure/zero.

`art-provenance.json` contains `candidate_identity` and roles `jaw`, `tooth`, `eye`, `ghost_head`, `ghost_body`, `fruit_body`, `fruit_crown`, `wall`, `floor`, `gate`, `pickup`, `life_icon`. Each maps `runtime_resource_fragments` and `derivation_verified` to public source art with source/candidate hashes or a reviewed derivation chain. Hash equality is only one possible provenance proof. The actual renderer receipt and visible frame must corroborate use; stored assets alone earn no credit.

Keep each scaffold's adapter, binding, provenance review and health receipts under that scaffold's evaluation directory. Never put them into its `input/`, another model's input, Gold gameplay, or the public observation API. Unknown mappings cannot fall back to Gold names.
